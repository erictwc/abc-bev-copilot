# ABC-BEV-CO Order-to-Shelf Assistant: build spec

Put this file in an empty repo as `SPEC.md`, add `CLAUDE.md`, `TICKETS.md` and `DECISIONS.md` from this folder, then tell Claude Code: "Read SPEC.md, CLAUDE.md and TICKETS.md. Work on T0 only."

## 1. Why this exists

A portfolio project that shows, end to end, what an AI-enablement or business-transformation role asks for:

- an agent that answers from structured data (SQL tool calling) and from documents (retrieval)
- an evaluation harness with a written bar, a judge model and human spot checks
- a build-vs-buy comparison of three model paths (local Qwen, cloud Qwen, Claude API)
- cost discipline (per-question cost, hard monthly cap, a router)
- guardrails (read-only SQL, role-based access, prompt-injection defense)
- adoption (guides, training, a small pilot)

The company, brands, data and documents are 100% synthetic. No real company, employer or customer data appears anywhere in the repo.

Eric designs the system, sets the rules in the documents (drafted from his interview answers, D27), writes a core set of eval cases, makes the decisions, and writes the build-vs-buy memo. Claude Code writes most of the code under his direction.

## 2. The product

**Fictional company: ABC-BEV-CO**, an energy-drink brand owner that sells through distributors to retail chains and uses a co-packer to make product. Invent all brand and SKU names.

**User (v1): a Trade Development manager.** Sample questions:

- "Why is Brand X short at distributor Y, and whose action fixes it?" (SQL, plus a policy for who owns what)
- "What is our policy on changing a PO after the co-packer confirms it?" (retrieval)
- "Which promoted SKUs next month have less than two weeks of warehouse cover, and what does the allocation policy say to do?" (both)
- "What will next quarter's volume be?" (must decline: no forecast data)

**Behavior requirements.** The agent cites its evidence (document passage IDs and the SQL it ran), states a confidence note when evidence is thin, says "I don't know" rather than guess, and never invents a number.

**v2 adds a second question family: promo ROI** ("Did the October promo at Chain Z pay back?"), using the same tools, same adapter and one extra table.

### Documents (`docs_corpus/`, 20 to 30 short files)

Each file starts with a header `DOC-ID`, title, owner, effective date.

Claude Code drafts each one from his answers only, and he reviews every line.
- **Claude Code generates:** product sheets from `sku_master`.
- **One planted document** contains an injection sentence ("ignore previous instructions...") for the trap and defense tests.

## 4. Architecture

- Python 3.11+, few dependencies, each justified in `DECISIONS.md`.
- **Storage:** DuckDB for tables. A local vector store (Chroma or sqlite-vec, decide in `DECISIONS.md`) for document chunks. Use a local embedding model so embedding costs nothing.
- **Retrieval:** chunk, embed, top-k, score threshold. Chunk size and k are config values and are logged.
- **Tools:**
  - `run_sql(query)`: read-only connection, allow-listed tables, single statement only, row limit, timeout.
  - `search_docs(query, k)`: returns passage text and DOC-ID.
- **Loop:** plain model call, tool call, tool result, repeat until final answer. No framework in v1. Cap on steps per question.
- **Adapter (`agent/adapter.py`, under 100 lines):** one interface over three paths:
  - `local`: Ollama on the GEEKOM box, reached over the home network via `OLLAMA_HOST`
  - `cloud`: hosted Qwen through an OpenAI-compatible API (provider chosen in `DECISIONS.md`)
  - `claude`: Anthropic API
  The adapter returns text, tool calls, token counts, latency and dollar cost. It handles retries. No LiteLLM or similar.
- **Output:** answer, evidence (passage IDs and SQL text), confidence note.
- **CLI:** `python ask.py "question" --model local|cloud|claude`

## 5. Cost control

- A spend log table records every model call (model, tokens, cost, timestamp).
- A hard monthly cap, enforced in code: the adapter refuses to call a paid model once the cap is reached. Development stops at **$15**; the hosted demo has its own **$20**, counted on demo calls only (D115, which replaced the original $20 total with $5 for the demo).
- Report cost per question for every model in the README.

## 6. Evaluation

### Cases (`evals/cases.yaml`)

Each case has: id, category, question, expected answer, expected tool(s), source (passage ID or SQL), and notes.

**v1: 40 cases**

| Category | Count |
|---|---|
| SQL lookups | 10 |
| Document retrieval | 8 |
| Combined (SQL + documents) | 8 |
| Must-decline | 6 |
| Traps | 8 |

Traps include a misspelled SKU, an ambiguous distributor, the planted injection document, the missing-month data problem, and the contradictory PO status.

**v2 adds 16:** 6 access-control bypass attempts and 10 promo-ROI cases.

**Authorship:** Eric hand-writes 20 cases first. Claude Code drafts 20 more, and Eric reviews every one line by line before it counts.

### Scoring

- SQL and numeric answers: exact or tolerance match.
- Text answers: rubric check by a judge model that is **a different model from the one being tested**.
- Eric hand-checks 10 judge calls and records disagreements in `evals/JUDGE_CHECK.md`.
- Per case, record: pass/fail, tools chosen, citation correct, latency, tokens, dollar cost.

### The bar (written before the first full run)

`evals/BAR.md` is committed before any full results exist:

- Claude path: at least 85% overall.
- 100% on must-decline cases and on the injection trap, for every path that is claimed to be safe.
- Local and cloud Qwen: no pass/fail bar. Report as measured.

The real number is reported whether or not the bar is hit. Results are committed to the repo after every meaningful change so the history shows improvement.

## 7. Hardware benchmark and GPU projection

- `bench/` holds a wrapper around `llama-bench` (or equivalent) that records prefill and decode tokens/second for each tested model size at several context lengths on the GEEKOM A5 (Ryzen 5 7430U, 16 GB RAM, Ubuntu).
- Model sizes to test are chosen after the first benchmark run. Plan for 7 to 8B at 4-bit; a 14B at 4-bit may fit but is tight; 32B will not fit. Verify current Qwen model names at build time.
- `bench/PROJECTION.md` estimates GPU performance from the box's measurements:
  - **decode** is limited by memory bandwidth: scale by the ratio of GPU to box memory bandwidth, then apply a realistic efficiency factor
  - **prefill** is limited by compute: scale by the ratio of compute throughput, which gives a much larger gap
  - take bandwidth and compute figures from vendor spec sheets, cite them, and publish a range
  - label everything "projected, not measured"
- Quality does not change with hardware for the same model and quantization. Larger models' quality comes from the cloud Qwen runs.
- Optional: rent a GPU for about an hour, run the same benchmark, and compare to the projection.
- Local runs are an overnight batch, not interactive.
