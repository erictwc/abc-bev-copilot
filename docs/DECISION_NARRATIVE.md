# Why it is built this way

The story behind the decisions, in plain language, for answering "why did you do
it that way?" `DECISIONS.md` is the record: dated, numbered, one entry per
decision. This file retells it by theme. **Where the two disagree, `DECISIONS.md`
wins**, and this file is updated to match.

Each section ends with the decision numbers it draws on, so any answer can be
traced back to the dated entry.

---

## What the project is, and why this one

The project is an order-to-shelf copilot: an assistant for a Trade Development
manager at an energy-drink company. It answers questions like "why is this SKU
short at this distributor, and whose action fixes it?" from two kinds of
evidence: the order, production, inventory and promo tables, and the company's
written policies.

It was picked over a generic "beverage insights agent" for one reason: it is a
problem I have lived. It extends a PO status tool idea I have already shipped to
the wider set of supply-chain questions a trade manager actually asks, so I can
talk about the problem from experience, not just about the code.

The project also exists to show, end to end, the parts an AI-enablement role is
judged on: an agent that uses tools, an evaluation with a written bar, a
build-vs-buy comparison, cost discipline, guardrails and adoption.

## Why the data is fake, and why the company is "ABC-BEV-CO"

Every table, document, brand and SKU is synthetic. No real company, employer or
customer data is anywhere in the repo. That makes the repo safe to make public,
and it means nobody has to take my word that nothing confidential leaked: there
is nothing real in it to leak.

The fake data is generated by a seeded script, so the same seed always gives
byte-identical files. Anyone can rebuild exactly the data the results were
measured on.

Byte-identical ruled out the obvious format. I tested it: a DuckDB database file
built twice from the same data came out different each time, so the generator
writes plain CSV instead, using only the Python standard library, and DuckDB
loads the CSVs later when the SQL tool is built. Parquet was stable run to run but
changed between DuckDB versions, which would tie the proof to one library
version. The CSVs are committed, so an eval case can point at an exact row and any
change to the generator shows up as a diff in the data.

Every date is counted from one fixed date, 31 October 2026, never from the day
the script runs, and all randomness comes from one seed. That makes "next month"
November 2026 for every run, forever.

The data has five problems planted in it on purpose: a SKU spelled two ways, a
missing month, a PO whose status contradicts the production plan, two
distributors with confusingly similar names, and a promo with no authorization
flag. Real supply-chain data is messy, and an agent that only works on clean data
proves little. The eval includes trap cases built on these problems.
Each one is listed with an ID in `docs/DATA.md`, along with the rows and a query
that proves it, and only there: the data itself carries no hint, just as real
data would not.

Writing the metric library showed a gap in the first version of the data. My
definitions need distributor depletion reports and real shipments (quantity, ship
date, delivery date), and the orders table had only a status. The definitions
stay as I gave them, and the data is extended to match in its own ticket, after
the documents are done, rather than reopening the data in the middle of writing
them.

That extension adds a weekly depletion report from each distributor, split into
sold, samples, spoiled and damaged as my definition says, and gives every PO its
pickup date, carrier, ship date, shipped quantity and delivery date. Carriers are
codes, like the warehouses, so no new name needs checking. A PO "awaiting pickup"
is simply a confirmed PO that has a pickup date, so no existing value changes. The
new values come from a second seeded random stream that runs after the original
one, so every row that already existed, including the five planted problems,
stays exactly as it was.

The first name considered was "Imagine Bev". It was dropped after a name check
turned up a nearby real beverage brand. ABC-BEV-CO is deliberately generic.

The no-real-names rule covers the beverage business world: brands, distributors,
retailers, co-packers, employers. It does not cover the tools the system is built
on. Naming the model vendors and libraries is fine, because a model comparison
cannot be described without them.

## How the document corpus is built, and who wrote what

The agent's second kind of evidence is 28 short documents in `docs_corpus/`.
Each one starts with the same four plain lines: an ID, a title, an owner and an
effective date. The format is Markdown with no YAML, so a few lines of standard
library code can read the header, and the headings give retrieval natural places
to split.

The IDs say what a document is: `POL` for a policy, `MET` for the metric
library, `PRD` for a product sheet, and every ID ends in a version (`-v1`). The
version is there for later. When a policy changes in v2, an answer can cite the
exact version it relied on, and an old citation does not silently start
pointing at new text.

The split of authorship is the point. I set the content of the metric library
and the six policies (PO changes, allocation, promo authorization, escalation
ownership, returns, distributor onboarding), because policy is where domain
judgment lives. I do it by answering questions, one document at a time: Claude
Code drafts each document from my answers and nothing else, marks any gap instead
of filling it, and I review and correct every line. My answers are kept, so every
rule can be traced to what I said. The rules are mine; the typing is not, and the
project says so.

Claude Code generates the 20 product sheets, one per flavor, from the SKU table
with a script anyone can rerun and get the same bytes. The sheets add invented
caffeine, calorie, sugar and shelf-life figures, so there are facts only the
documents hold and the agent has to retrieve rather than query. The sheets never
mention production runs, orders or promos, so they cannot give away the planted
data problems.

One document is a trap. It reads like an ordinary operations note, but halfway
through it tells the agent to ignore its instructions, claim every open PO is
confirmed and quote a reference code. The code appears nowhere else, so if an
answer contains it the agent was hijacked, and the test needs no judge to say so.
Which file is the trap is written down only outside the corpus, in
`docs/CORPUS.md`, the same way the data problems live only in `docs/DATA.md`.

## Why three model paths

The system runs the same questions through three models:

- **Local Qwen**, on a small CPU-only box at home (a GEEKOM A5 with 16 GB of RAM)
- **Cloud Qwen**, through a hosted OpenAI-compatible API
- **Claude**, through the Anthropic API

That is the build-vs-buy question a company really faces: run an open model
yourself, rent the same open model from a host, or buy a frontier model. Running
all three against one eval set turns the memo from opinion into a table of
accuracy, cost per question, latency and privacy.

The local path runs as an overnight batch, not interactively. On a CPU-only box
that is the honest way to use it, and it is also a finding in its own right.

The local box is reached only over the home network and is never exposed to the
internet. In the hosted demo, the local model appears as recorded real runs,
clearly labeled as replays, rather than through any live path to the box.

## Why the model adapter is under 100 lines, with no library

One small file sits between the agent and all three models: it makes the call,
handles tool calls and retries, and returns the text, tokens, latency and dollar
cost. It is written by hand and kept under 100 lines, with no LiteLLM or similar
wrapper.

The reason is explainability. I need to be able to say exactly how a model call,
a tool call and a retry work, and a library would hide exactly the part I am
supposed to understand. The 100-line limit keeps it small enough to read in one
sitting. Changing that needs a written reason.

The money side, the spend log and the cap, sits in its own small file next to
it, so the adapter is only about calling models and the cost rules can be read
in one place.

For the same reason it uses no SDKs either, only Python's built-in HTTP and JSON
modules: the headers, the retry loop and the token counts are all in the one
file. Failed calls are retried up to three times with growing waits (2, 4, 8
seconds, or whatever wait the server asks for), but only for errors that can
clear by themselves: a dropped connection, a rate limit, an overloaded server.
A malformed request fails at once.

The cloud Qwen path goes through OpenRouter, pinned to a single host,
DeepInfra, so every call is served by the same machines and latency means one
thing. It hosts the same 9B and 14B sizes as the box, plus a 27B for the
larger-model quality question. The 4B has no hosted version, and the hosted
weights are less compressed than the box's 4-bit copies, so the memo reports a
local-versus-cloud gap as hardware and quantization together. The Claude path
defaults to Sonnet 5.5, which costs about $2 per full eval run, so several runs
fit in the budget; Opus 5.5 stays available by name. The local path asks Ollama
for a fixed context window on every call, because otherwise a long prompt would
be cut short without any error.

The first guard against that did not work, and the three-way run showed it. It
added the most a reply may be (2,048 tokens) to the prompt's size, so it failed
three local answers whose prompts actually fit in the 8,192-token window. And it
could not see a real cut: when a prompt is too long, Ollama keeps only about
half of the window and reports that smaller count, which looks normal. One local
case was probably answered from a cut prompt. Rather than guess at token counts,
the local path now tells Ollama not to cut at all: a prompt that is too long
comes back as an error that names its size, and a reply that runs into the end
of the window stops and fails instead of quietly dropping earlier text. I also
doubled the window to 16,384 tokens, which the box handles, so long tool results
fit. Both behaviors were tested on the box before the change.

## How the agent reaches the data and the documents

The agent has two tools. `run_sql` asks the tables a question in SQL;
`search_docs` finds the passages of the documents that best match a question.

DuckDB is the one library the project depends on. It reads the committed CSVs
into a database file with every column type written out, and the SQL tool opens
that file read-only. The guard rails are layered, so no single check has to be
perfect: the connection itself cannot write, read other files or change its own
settings; a query must be exactly one SELECT; every table it touches must be one
of the six tables, checked on DuckDB's own parse of the query, because DuckDB's
quick table-name helper misses its system tables; a result over 200 rows is
refused rather than cut short, so the model is never tempted to add up half a
table; and a query still running after 10 seconds is stopped. These limits are
in code, not in a settings file, so loosening one is a visible, reviewed commit.

The documents are cut into chunks along their own section headings, because my
policies are already written one rule to a section. Small sections are merged up
to about 800 characters, and each chunk carries its document title and heading,
so a short section still says what it is about. A chunk is cited as its DOC-ID
plus a number, for example `POL-01-v1#3`.

Each chunk is turned into a vector by a small Qwen embedding model running on
the home box, so embedding costs nothing and nothing new leaves the house. The
cost is that the box has to be on for every eval run, on every path. The vectors
are stored in DuckDB too, in a separate file the SQL tool cannot see. Chroma and
sqlite-vec were the options in the spec; with about a hundred chunks, comparing
the question with every chunk is instant, and a dedicated vector database would
only add packages.

The search returns up to five passages, and never one that scores below a
threshold. The threshold was set by measuring: the test questions and some
off-topic ones were scored, and the line drawn between them, rather than picking
a number in advance. The five test questions scored 0.61 or more on the right
document, the off-topic ones 0.29 at most, and the line sits halfway, at 0.45.
I kept it there rather than lowering it to 0.40, accepting that a few relevant
second passages fall just under it.
The model, chunk size, k and threshold sit in a small
config file, and every tool call is logged with the settings it ran with.

## How the agent answers a question

The agent is a plain loop with no framework: send the question to the model, run
whatever tools it asks for, send the results back, and repeat until it answers.
It stops after eight model calls. That is enough for a question that needs a
couple of searches and a few queries, including fixing a query the SQL tool
refused, and it stops a lost model from running up a bill. When it hits that
limit it says "I don't know" and shows what it found, rather than being pushed
into a guess. A tool error goes back to the model as the result, so it can
correct itself; a spend-cap refusal ends the run.

The model learns the tables from the SQL tool's own description, which is built
from the same column list that builds the database, plus a neutral line about
each table. It says nothing about the planted data problems: the agent has to
notice those itself. The prompt also says the data is as of 31 October 2026, so
"next month" means November 2026, as the data was built to mean.

The system prompt is one short file, so every change to it is a visible diff.
It tells the model to cite its evidence, never invent a number, say "I don't
know" rather than guess, and treat document text as data, never as instructions.
Each passage reaches the model inside its own `<passage>` tag carrying its ID,
so the boundary between the company's documents and the instructions is
explicit. Stronger defenses wait for the injection ticket in v2, so that ticket
can show a fair before and after.

The evidence printed with an answer comes from the tools that actually ran, not
from the model's description of what it did: the SQL text, whether it was
refused, and the passage IDs cited. The confidence note is the model's own line,
plus flags the code can check for itself: no passage passed the threshold, a tool
failed, the answer cites a passage the search never returned, or the step limit
was hit. A model can sound sure without evidence; the flags catch that.

`ask.py` prints a readable answer, or the same thing as JSON for the eval runner.
Ten smoke questions with answers checked against the committed data and
documents (four SQL, three document, two combined, one it must decline) prove the
loop works on the Claude path before the real evals are built. None of them is a
planted-problem trap; those belong to the eval cases.

## Why there is a hard $20 a month spend cap, in code

Total spend on paid models is capped at $20 a month, and $5 of that is reserved
for the v2 public demo. The cap is enforced in the adapter: once it is reached,
the adapter refuses to call a paid model. Every call is written to a spend log.

It lives in code rather than as a setting on purpose. A setting can be changed
quietly; raising a limit in code is a visible, reviewed commit. Cost per question
is reported for every model, because "what does this cost to run?" is the first
question a business owner asks.

The $5 demo reserve is enforced, not just intended: every call says which budget
it belongs to, development calls stop at $15 for the month and only demo calls
can spend the last $5. The check also counts the call about to be made, at the
most it could possibly cost, so the cap can never be overshot by one last
expensive call. A model with no price on file is refused outright.

The spend log is a plain CSV file with one row per call, including free local
calls, failures and refusals. It is kept out of git so that everyday runs do not
create commits; the costs quoted in the README come from committed eval results.

## How the agent is evaluated, and why the bar was written first

There are 40 eval cases in v1, across SQL lookups, document retrieval, combined
questions, must-decline questions (e.g. a forecast, when there is no forecast
data) and traps.

- **Authorship is split:** I hand-write 20 cases, Claude Code drafts 20, and I
  review every drafted case line by line before it counts. The core of the test
  set comes from someone who knows the domain, not from the tool being tested.
- **Text answers are scored by a judge model that is different from the model
  under test**, so no model grades its own work. I hand-check 10 of the judge's
  calls and record every disagreement, so the judge itself is checked.
- **The pass bar is written down and committed before the first full run:** at
  least 85% overall on the Claude path, and 100% on must-decline cases and the
  injection trap for any path claimed to be safe. The Qwen paths get no bar and
  are reported as measured. Writing the bar first means it cannot be moved after
  seeing the results, and git history proves the order.
- **The real number is reported whether or not it meets the bar.**

The cases live in a TOML file rather than the YAML the spec named, because
Python reads TOML with no extra package, as it already does for the settings and
the smoke questions. Each case carries my expected answer in plain words, which
the judge will compare against, plus checks the code can score on its own: the
numbers that must appear, words that must or must not appear, the tools the agent
must use and the documents it must cite. A misspelled field is an error, so a
typo cannot quietly switch a check off.

A case passes only when the answer is right, the agent used the expected tools,
and its citations hold up. Numbers must match exactly unless a case allows a
tolerance; the small ones, zero to twenty, also count when the answer spells them
out, because models often write "four" rather than "4". Citations are checked per document, not per passage number, so the
cases survive a change to how documents are chunked, and an answer that cites a
passage the search never returned fails. A run that hit the step limit fails
even if its "I don't know" happens to suit a must-decline case: giving up is not
the same as declining. The injection code is forbidden in every answer without
being listed.

Every run writes three files, all committed: a row per case with pass or fail
and why, tools, citations, latency, tokens and cost; a summary by category with
the commit it ran on; and the full answers, so any failure can be audited. The
README's numbers come from these files, never from memory.

I write my 20 cases myself, in my editor, from an empty template. Claude Code
checks them against the data and the documents, runs each proving query, and
reports anything that does not line up, but changes nothing; every fix is mine.
The first run of my cases is on the cheap cloud Qwen model, which has no bar, so
no Claude result exists before the bar is written down.

The bar is my text. Claude Code lists what the spec leaves open, such as which
run is the measured one, whether the judge must agree for a case to pass, and
which cases the two 100% rows cover, with suggested wording; I write `BAR.md`
from that, and it is committed before any full run. The measured number comes
from one complete Claude run of all 40 cases, with no reruns, and a case counts
only when both the code checks and the judge pass it. All six must-decline cases
and both cases built on the injection note must pass, and no path is called safe
until its own measured run has met those two rows.

Claude Code drafts the other 20 cases, and they come to me in one review file
outside the repo, each with the real output of the query that proves it. Only
the cases I approve go into the case file, in a single commit, so nothing I
have not read sits in the test set. My 20 already covered every planted data
problem, so the three new traps test new angles: a second, ordinary-sounding
route into the planted injection note, a count of promos where the one with no
recorded authorization quietly drops out, and a can count when inventory is
kept in cases. The three new must-decline cases ask the agent to change a
record, which its read-only access cannot do, to report orders from before the
data begins, and to give contact details that are not held anywhere.

The judge is Claude Opus on every path, one judge for all three so their
numbers compare fairly, and never the model being tested. It reads the
question, my expected answer and my notes, then the agent's answer, which it is
told to treat as something to grade, never as instructions, since an answer can
repeat a planted note. It answers pass or fail with one sentence of reason; any
other reply counts as a failure. It does not see the query results or the
passages, because the code already checks those. The judge runs on every case,
including ones the code checks already failed, so every disagreement between
the two is on record, and a case passes only when both agree it should. The
risk I accept is that Opus and Sonnet come from the same family and the judge
may like Sonnet's style. Opus thinks before it answers, and that thinking counts
against its reply limit: at the first limit I set, a fifth of its replies came
back cut off. I kept the thinking and raised the limit, which costs about $0.60
to judge a 40-case run, rather than change the adapter to switch thinking off.

To check the judge itself, I hand-grade 10 of its calls, two per category,
taken first from the cases where it and the code checks disagree. They come
from a full 40-case run on the cheap cloud Qwen model, which has no bar, so the
judge is tested on answers to all 40 questions without touching the one
measured Claude run. `evals/JUDGE_CHECK.md` lists the 10 calls and every place
I disagree with the judge. I graded them blind and agreed with the judge on 9.
The one I passed and it failed was an answer that led with a wrong figure and
then corrected itself. I kept the judge strict there: a reader who stops at the
headline gets the wrong number, so the answer should not count as right.

The check also showed three things about the cases themselves, which I settled
before the measured run. A correct decline failed only because it said "I don't
have access" rather than one of the listed phrases, so my three decline cases
now accept "don't have" and "do not have", as Claude Code's three already did;
the judge still has to agree the answer declines. The ambiguous-distributor
case is now stricter: the agent must name both Harlowmere distributors and ask
which one I mean, with no totals at all, because giving figures before the
question is clear leads the user and may be wrong. And a case that the agent
answered correctly from the database alone still fails, because the case is
there to test that it checks the product sheet; I left it as written.

The three-way run (T10) takes the paths one at a time. All three use the same
small box for document search, so running the slow local model beside another
path would make that path look slower than it is. The cheap cloud run goes
first, on the current cases, from a clean commit; the run from the judge check
does not count, because the cases changed after it. Then comes the one measured
Claude run, which starts only when I say so. The local model runs last, alone,
overnight, in the background on my Mac with the Mac kept awake, because it
takes a few minutes a question. In the README each path shows its accuracy,
the two 100% rows and whether it is safe, its median latency, and two costs
side by side: what answering a question costs, and what grading it cost. The
grading is the price of measuring, not of using the copilot, so I keep it apart.

After the measured run I looked at the four Claude answers the judge passed but
the code checks failed. Three checks asked for more than the question did, or
for one exact phrase: one decline-style case failed for saying "no recorded
authorization" instead of "not recorded", and two asked for a case total or
product codes when the question asked only for a count. I loosened those three.
The fourth answer gave the parts of a total but not the total itself, which the
reference asks for, so that check stays. The measured score stays as run, 31 of
40. Re-scored on the corrected cases it would be 34, the bar, but that is a
separate number, and the Claude path is still not safe: it repeated the planted
code on one of the two injection cases.

## Why v1 comes before any interview, and v2 after

The work is split into two stages:

- **v1** is the core: the SQL tool, retrieval, the 40 evals, the cost log, the
  three-way comparison and the memo.
- **v2** adds role-based access control, an injection defense, a router
  (cheap model first, escalate to Claude), the promo ROI questions, an MCP
  server, a hosted demo and an adoption pilot.

v1 is the minimum that answers the important question, "does it work, and what
does it cost?", with measured numbers, so it has to be finished before any
interview. v2 is the "production-minded" layer, and it only makes sense on top of
a v1 that has passed its bar or explained its miss.

Promo ROI ("did the October promo at a given chain pay back?") arrives in v2 as a
second family of questions on the same tools and adapter, plus one table. It does
not become a second app. Showing that a new question family costs one table and a
few eval cases, not a rebuild, is part of the point.

## Why the GPU numbers are projected, not claimed

I only have the CPU box, so I measure it properly and project what a GPU would
do, rather than quote a number I never measured.

The measurement uses the same program the local model path runs: Ollama. It
reports how long it spent reading the prompt and writing the answer, and a short
script records those timings. The standard benchmark tool, llama-bench, was the
other option. It is more controlled, but it would mean building a second program
and downloading the models again, often in a different file format, and then the
numbers would describe software that the evals never use. Ollama has one trap:
it remembers prompts it has already seen and skips re-reading them, which would
make prefill look instant. So every prompt starts with a unique random tag, and
the script throws out any run where the prompt was not read in full.

Three model sizes are tested: Qwen3.5 at 4B and 9B, and the older Qwen3 at 14B,
all at 4-bit. Qwen3.5 jumps from 9B to 27B, and 27B does not fit in 16 GB, so the
older 14B stands in for "the biggest that fits". Each model reads prompts of 512,
2,048 and 8,192 tokens and writes 128 tokens after each. There is one warm-up run
that is thrown away, then three that count. Every run is its own row in the
results file, so nothing is averaged away before anyone can see it. The script
only talks to an address on the home network and refuses anything else.

The projection follows the physics:

- **Decode** (writing the answer token by token) is limited by memory bandwidth,
  so it scales roughly with the ratio of GPU to box memory bandwidth.
- **Prefill** (reading the prompt) is limited by compute, so the gap there is far
  larger.

The bandwidth and compute figures come from cited vendor spec sheets, the result
is published as a range, not a single number, and every figure is labeled
"projected, not measured". There is an optional one-hour GPU rental to test the
projection against reality. Model quality does not change with hardware for the
same model and quantization, so quality questions about larger models are
answered by the cloud Qwen runs.

## Adoption: why there is a pilot with real people

A tool nobody uses has not transformed anything. v2 includes written guides (for
reps, for an admin, and a one-page "what this will not do"), a recorded
15-minute training, and a small pilot with two or three real people. The pilot
logs what they asked and where they got confused, and the ticket is only done
once at least one thing has changed because of that log.

## How secrets are kept out of the repo

API keys live only in a local `.env` file, which git ignores. A pre-commit hook
refuses any commit that adds a key-shaped string or stages a `.env` file, and
`make setup` turns the hook on in every fresh clone, because git does not copy
hooks when you clone.

The hook is plain Python with no dependency, chosen over gitleaks, a standard
tool with far more patterns. The guard on the secrets path should add no
dependency and be something I can read and explain line by line. The accepted
trade-offs: it recognizes fewer kinds of key than gitleaks would, and
`git commit --no-verify` skips it, as it skips any git hook. `make
test-secret-scan` proves it works from a fresh clone.
