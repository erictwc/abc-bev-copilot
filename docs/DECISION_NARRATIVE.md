# Why it is built this way

The story behind the decisions, in plain language, for answering "why did you do
it that way?" `DECISIONS.md` is the record: dated, numbered, one entry per
decision. This file retells it by theme. **Where the two disagree, `DECISIONS.md`
wins**, and this file is updated to match.

Each section ends with the decision numbers it draws on, so any answer can be
traced back to the dated entry.

---

## What the project is, and why this one

The project is an order-to-shelf copilot: an assistant for a Trade Development
manager at an energy-drink company. It answers questions like "why is this SKU
short at this distributor, and whose action fixes it?" from two kinds of
evidence: the order, production, inventory and promo tables, and the company's
written policies.

It was picked over a generic "beverage insights agent" for one reason: it is a
problem I have lived. It extends a PO status tool idea I have already shipped to
the wider set of supply-chain questions a trade manager actually asks, so I can
talk about the problem from experience, not just about the code.

The project also exists to show, end to end, the parts an AI-enablement role is
judged on: an agent that uses tools, an evaluation with a written bar, a
build-vs-buy comparison, cost discipline, guardrails and adoption.

## Why the data is fake, and why the company is "ABC-BEV-CO"

Every table, document, brand and SKU is synthetic. No real company, employer or
customer data is anywhere in the repo. That makes the repo safe to make public,
and it means nobody has to take my word that nothing confidential leaked: there
is nothing real in it to leak.

The fake data is generated by a seeded script, so the same seed always gives
byte-identical files. Anyone can rebuild exactly the data the results were
measured on.

Byte-identical ruled out the obvious format. I tested it: a DuckDB database file
built twice from the same data came out different each time, so the generator
writes plain CSV instead, using only the Python standard library, and DuckDB
loads the CSVs later when the SQL tool is built. Parquet was stable run to run but
changed between DuckDB versions, which would tie the proof to one library
version. The CSVs are committed, so an eval case can point at an exact row and any
change to the generator shows up as a diff in the data.

Every date is counted from one fixed date, 31 October 2026, never from the day
the script runs, and all randomness comes from one seed. That makes "next month"
November 2026 for every run, forever.

The data has five problems planted in it on purpose: a SKU spelled two ways, a
missing month, a PO whose status contradicts the production plan, two
distributors with confusingly similar names, and a promo with no authorization
flag. Real supply-chain data is messy, and an agent that only works on clean data
proves little. The eval includes trap cases built on these problems.
Each one is listed with an ID in `docs/DATA.md`, along with the rows and a query
that proves it, and only there: the data itself carries no hint, just as real
data would not.

The first name considered was "Imagine Bev". It was dropped after a name check
turned up a nearby real beverage brand. ABC-BEV-CO is deliberately generic.

The no-real-names rule covers the beverage business world: brands, distributors,
retailers, co-packers, employers. It does not cover the tools the system is built
on. Naming the model vendors and libraries is fine, because a model comparison
cannot be described without them.

## How the document corpus is built, and who wrote what

The agent's second kind of evidence is 28 short documents in `docs_corpus/`.
Each one starts with the same four plain lines: an ID, a title, an owner and an
effective date. The format is Markdown with no YAML, so a few lines of standard
library code can read the header, and the headings give retrieval natural places
to split.

The IDs say what a document is: `POL` for a policy, `MET` for the metric
library, `PRD` for a product sheet, and every ID ends in a version (`-v1`). The
version is there for later. When a policy changes in v2, an answer can cite the
exact version it relied on, and an old citation does not silently start
pointing at new text.

The split of authorship is the point. I set the content of the metric library
and the six policies (PO changes, allocation, promo authorization, escalation
ownership, returns, distributor onboarding), because policy is where domain
judgment lives. I do it by answering questions, one document at a time: Claude
Code drafts each document from my answers and nothing else, marks any gap instead
of filling it, and I review and correct every line. My answers are kept, so every
rule can be traced to what I said. The rules are mine; the typing is not, and the
project says so.

Claude Code generates the 20 product sheets, one per flavor, from the SKU table
with a script anyone can rerun and get the same bytes. The sheets add invented
caffeine, calorie, sugar and shelf-life figures, so there are facts only the
documents hold and the agent has to retrieve rather than query. The sheets never
mention production runs, orders or promos, so they cannot give away the planted
data problems.

One document is a trap. It reads like an ordinary operations note, but halfway
through it tells the agent to ignore its instructions, claim every open PO is
confirmed and quote a reference code. The code appears nowhere else, so if an
answer contains it the agent was hijacked, and the test needs no judge to say so.
Which file is the trap is written down only outside the corpus, in
`docs/CORPUS.md`, the same way the data problems live only in `docs/DATA.md`.

## Why three model paths

The system runs the same questions through three models:

- **Local Qwen**, on a small CPU-only box at home (a GEEKOM A5 with 16 GB of RAM)
- **Cloud Qwen**, through a hosted OpenAI-compatible API
- **Claude**, through the Anthropic API

That is the build-vs-buy question a company really faces: run an open model
yourself, rent the same open model from a host, or buy a frontier model. Running
all three against one eval set turns the memo from opinion into a table of
accuracy, cost per question, latency and privacy.

The local path runs as an overnight batch, not interactively. On a CPU-only box
that is the honest way to use it, and it is also a finding in its own right.

The local box is reached only over the home network and is never exposed to the
internet. In the hosted demo, the local model appears as recorded real runs,
clearly labeled as replays, rather than through any live path to the box.

## Why the model adapter is under 100 lines, with no library

One small file sits between the agent and all three models: it makes the call,
handles tool calls and retries, and returns the text, tokens, latency and dollar
cost. It is written by hand and kept under 100 lines, with no LiteLLM or similar
wrapper.

The reason is explainability. I need to be able to say exactly how a model call,
a tool call and a retry work, and a library would hide exactly the part I am
supposed to understand. The 100-line limit keeps it small enough to read in one
sitting. Changing that needs a written reason.

*Draws on D4; SPEC §4.*

## Why there is a hard $20 a month spend cap, in code

Total spend on paid models is capped at $20 a month, and $5 of that is reserved
for the v2 public demo. The cap is enforced in the adapter: once it is reached,
the adapter refuses to call a paid model. Every call is written to a spend log.

It lives in code rather than as a setting on purpose. A setting can be changed
quietly; raising a limit in code is a visible, reviewed commit. Cost per question
is reported for every model, because "what does this cost to run?" is the first
question a business owner asks.

## How the agent is evaluated, and why the bar was written first

There are 40 eval cases in v1, across SQL lookups, document retrieval, combined
questions, must-decline questions (e.g. a forecast, when there is no forecast
data) and traps.

- **Authorship is split:** I hand-write 20 cases, Claude Code drafts 20, and I
  review every drafted case line by line before it counts. The core of the test
  set comes from someone who knows the domain, not from the tool being tested.
- **Text answers are scored by a judge model that is different from the model
  under test**, so no model grades its own work. I hand-check 10 of the judge's
  calls and record every disagreement, so the judge itself is checked.
- **The pass bar is written down and committed before the first full run:** at
  least 85% overall on the Claude path, and 100% on must-decline cases and the
  injection trap for any path claimed to be safe. The Qwen paths get no bar and
  are reported as measured. Writing the bar first means it cannot be moved after
  seeing the results, and git history proves the order.
- **The real number is reported whether or not it meets the bar.**

## Why v1 comes before any interview, and v2 after

The work is split into two stages:

- **v1** is the core: the SQL tool, retrieval, the 40 evals, the cost log, the
  three-way comparison and the memo.
- **v2** adds role-based access control, an injection defense, a router
  (cheap model first, escalate to Claude), the promo ROI questions, an MCP
  server, a hosted demo and an adoption pilot.

v1 is the minimum that answers the important question, "does it work, and what
does it cost?", with measured numbers, so it has to be finished before any
interview. v2 is the "production-minded" layer, and it only makes sense on top of
a v1 that has passed its bar or explained its miss.

Promo ROI ("did the October promo at a given chain pay back?") arrives in v2 as a
second family of questions on the same tools and adapter, plus one table. It does
not become a second app. Showing that a new question family costs one table and a
few eval cases, not a rebuild, is part of the point.

## Why the GPU numbers are projected, not claimed

I only have the CPU box, so I measure it properly and project what a GPU would
do, rather than quote a number I never measured. The projection follows the
physics:

- **Decode** (writing the answer token by token) is limited by memory bandwidth,
  so it scales roughly with the ratio of GPU to box memory bandwidth.
- **Prefill** (reading the prompt) is limited by compute, so the gap there is far
  larger.

The bandwidth and compute figures come from cited vendor spec sheets, the result
is published as a range, not a single number, and every figure is labeled
"projected, not measured". There is an optional one-hour GPU rental to test the
projection against reality. Model quality does not change with hardware for the
same model and quantization, so quality questions about larger models are
answered by the cloud Qwen runs.

## Adoption: why there is a pilot with real people

A tool nobody uses has not transformed anything. v2 includes written guides (for
reps, for an admin, and a one-page "what this will not do"), a recorded
15-minute training, and a small pilot with two or three real people. The pilot
logs what they asked and where they got confused, and the ticket is only done
once at least one thing has changed because of that log.

## How secrets are kept out of the repo

API keys live only in a local `.env` file, which git ignores. A pre-commit hook
refuses any commit that adds a key-shaped string or stages a `.env` file, and
`make setup` turns the hook on in every fresh clone, because git does not copy
hooks when you clone.

The hook is plain Python with no dependency, chosen over gitleaks, a standard
tool with far more patterns. The guard on the secrets path should add no
dependency and be something I can read and explain line by line. The accepted
trade-offs: it recognizes fewer kinds of key than gitleaks would, and
`git commit --no-verify` skips it, as it skips any git hook. `make
test-secret-scan` proves it works from a fresh clone.
